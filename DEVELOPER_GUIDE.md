# EPBossAuction — инструкция для разработчика

Гильдейский аддон для WotLK 3.3.5a: рейдеры делают ставки EP на лут по EPGP,
Loot Master видит список ставок по каждому предмету каждого босса и раздаёт
лут вручную (аддон **не** раздаёт лут и не списывает EP сам — только
показывает, кто сколько поставил).

Этот файл — не техдокументация по каждой строчке (это делают комментарии в
самом коде), а карта: что где искать, как это всё связано и на что не
наступить при доработке.

## Файлы и их зоны ответственности

| Файл | Что внутри |
|---|---|
| `core.lua` | Глобальная таблица `EPBossAuction` (везде далее — `auction`). Список боссов/предметов (`auction.bosses`), дефолтные настройки (`auction.defaults`), явка на босса, версия аддона + changelog, утилиты (`CompareVersions`, `FormatNumber`, `DeepCopy`, `MergeDefaults`), загрузка/сохранение SavedVariables. |
| `comm.lua` | Весь сетевой протокол: отправка (`SendAddonMessage`) и приём (`Handle_*`). См. таблицу команд в шапке файла и ниже в этой инструкции. |
| `ui.lua` | Главное окно, таблица предметов, кнопки явки, окно "Что нового?", слэш-команды. Не трогает сеть напрямую — вызывает функции из `comm.lua`. |
| `events.lua` | Единственная точка входа: один фрейм, один `OnEvent`, реагирует на `ADDON_LOADED`, `PLAYER_ENTERING_WORLD`, `CHAT_MSG_ADDON`, `GROUP_ROSTER_UPDATE`/`RAID_ROSTER_UPDATE`, `PLAYER_LOGOUT`, `EPGP_UPDATE`. |
| `epgp.lua` | Мост к внешнему EPGP-аддону (EPGP / EPGP_Auction / CEPGP / EPGPCore) — получение EP игрока, с резолвом твинк → мейн. |
| `theme.lua` | Палитра + хелперы `SkinPanel`/`SkinButton`/`SkinInput`/`SkinCheckbox`/`SkinDropdown`/`SkinScrollBar` для единого тёмного стиля. |
| `options.lua` | Панель настроек (Interface Options → EPBossAuction). |
| `minimap.lua` | Кнопка на миникарте. |
| `attendance.lua` | Вкладка Attendance (только для ЛМ и офицеров): доступ, запись снимков состава рейда при очистке таблицы, подсчёт посещаемости (`BuildAttendanceReport` — чистая функция), вкладки главного окна и панель с таблицей. |
| `EPBossAuction.toc` | Манифест: версия, список файлов (порядок загрузки важен!), `SavedVariables`. |

**Правило**: данные — в `core.lua`, сеть — в `comm.lua`, отрисовка — в `ui.lua`.
Если добавляешь фичу и не понимаешь, в какой файл её класть — скорее всего,
она разъезжается на три части (структура данных / рассылка / кнопка), и это
нормально, так устроен весь остальной код.

## Данные: что и где хранится

Всё висит прямо на таблице `auction` (не через `self.db`, кроме настроек —
см. ниже), заполняется в `events.lua` при `ADDON_LOADED` из `SavedVariables`:

| Поле | Что это | SavedVariable |
|---|---|---|
| `auction.bids[boss][itemID]` | список `{player, amount, isOffspec}` — текущие ставки | `EPBossAuctionSavedBids` |
| `auction.signups[boss][category]` | `{[playerName] = true}` — явка (`fight`/`rest`/`valanyr`) | `EPBossAuctionSavedSignups` |
| `auction.dataVersions[boss:itemID]` | счётчик версии данных (у ЛМ растёт при каждой ставке) | `EPBossAuctionSavedVersions` |
| `auction.lastVersions[boss:itemID]` | последняя версия, которую **я** применил из SYNC | не сохраняется (сбрасывается при входе) |
| `auction.attendance` | список записей посещаемости, по возрастанию времени (формат — в шапке `attendance.lua`) | `EPBossAuctionSavedAttendance` |
| `auction.db` | настройки (см. `auction.defaults` в `core.lua`) | `EPBossAuctionSettings` |
| `auction.bidsLocked` | заблокированы ли ставки | `EPBossAuctionBidsLocked` |

`dataVersions` и `lastVersions` — разные вещи, их легко перепутать по
названию. Комментарий над этим блоком в `core.lua` объясняет разницу
подробнее.

`auction.bosses[bossName]` — статический список `itemID` по каждому боссу,
правится руками в `core.lua`. Если сервер меняет лут-таблицу боссов — тут и
поправлять.

`auction.instances[instanceName]` — группировка боссов по подземельям (для
дропдауна "Подземелье" → "Босс"). `auction.bossToInstance[bossName]` — обратный
индекс, нужен только для восстановления выбора при входе (`events.lua`).
Важно: сами данные (ставки/явка/версии/сеть) как хранились, так и хранятся по
`bossName`, подземелье в эти ключи не подмешивается — оно чисто для UI-группировки,
ничего в протоколе/SavedVariables из-за этого не менялось.

## Роль Loot Master (ЛМ)

`auction:IsLootMaster()` (`core.lua`) — **не** сетевой статус, а прямая
проверка через `GetLootMethod()`/раид-ростер: правда ли этот клиент сейчас
мастер-лут в понимании самого WoW. Это нельзя подделать по сети — кто угодно
может разослать сообщение `"LM"`, но `IsLootMaster()` у него всё равно вернёт
`false`, если он не мастер-лут на самом деле.

А вот `auction.lastLM` (от кого принимать `SYNC`) — **это** устанавливается
по сетевым сообщениям (`Handle_LM`/`Handle_LM_RESPONSE`) без проверки. Так и
задумано (см. следующий блок про `Handle_SYNC`), но если когда-нибудь
понадобится защита от подмены ЛМ по сети — копать нужно именно здесь, а не в
`IsLootMaster()`.

## Сетевой протокол

Все сообщения — через `SendAddonMessage(auction.prefix, ...)`, формат
`"КОМАНДА;параметр1;параметр2;..."`. Входящие приходят в `events.lua`
(`CHAT_MSG_ADDON`) → `auction:HandleMessage(msg, sender)` в `comm.lua`, которая
по первому слову до `;` находит и вызывает `auction:Handle_<КОМАНДА>(rest, sender)`.

**Чтобы добавить новую команду, ничего регистрировать не нужно** — просто
написать функцию `auction:Handle_ИМЯ(rest, sender)`, диспетчер найдёт её сам.

| Команда | Канал | Кто → кому | Зачем |
|---|---|---|---|
| `LM` | RAID | ЛМ → рейд | "Я лутер" |
| `LM_REQUEST` | WHISPER | игрок → ЛМ | "Кто у нас лутер?" |
| `LM_RESPONSE` | WHISPER | ЛМ → игрок | ответ на `LM_REQUEST` |
| `HELLO` | WHISPER | игрок → ЛМ | "Пришли данные по боссу X" (или без параметра — по всем) |
| `HELLO_ACK` | WHISPER | ЛМ → игрок | подтверждение получения `HELLO` |
| `CHECK_VERSION` | WHISPER | игрок → ЛМ | "Какие у тебя версии данных?" |
| `VERSIONS` | WHISPER | ЛМ → игрок | ответ на `CHECK_VERSION` |
| `BID` | WHISPER | игрок → ЛМ | ставка (`amount = 0` = отказ от ставки) |
| `BIDOK` | WHISPER | ЛМ → игрок | ставка принята |
| `TOOLOW` | WHISPER | ЛМ → игрок | ставка меньше минимальной |
| `SYNC` | RAID/WHISPER | ЛМ → все | полные данные по предмету + версия |
| `SYNC_COMPLETE` | RAID/WHISPER | ЛМ → все | "синхронизация завершена" |
| `LOCK` | RAID | ЛМ → рейд | блокировка/разблокировка ставок |
| `LOCKED` | WHISPER | ЛМ → игрок | "ставки сейчас заблокированы" (в ответ на BID во время лока) |
| `END` | RAID | ЛМ → рейд | очистка ставок+явки по одному боссу |
| `END_ALL` | RAID | ЛМ → рейд | очистка ставок+явки по всем боссам. Формат `END_ALL;<босс>`: параметр — босс, по которому раздавали лут (нужен вкладке Attendance), может быть пустым; старые версии аддона параметр игнорируют |
| `SIGNUP` | RAID | любой → рейд | явка (хочу бить/отдохнуть/валик) |
| `MY_VERSION` | **GUILD** | любой → гильдия | версия аддона (для уведомления об обновлении) |
| `OFFSPEC_MULT` | RAID | ЛМ → рейд | новый коэффициент офф-спека |

Обрати внимание: `MY_VERSION` — единственная команда на канале `GUILD`, все
остальные — `RAID`/`WHISPER`. Это осознанно: аддон гильдейский, а не только
рейдовый, и уведомление об обновлении должно доходить до всех в гильдии, а не
только до тех, кто сейчас в рейде.

### Важный неочевидный момент: `Handle_SYNC`

```lua
if version > lastVersion or senderIsLM then
```

Выглядит как баг (версия по факту не проверяется, если сообщение пришло от
текущего ЛМ), но это осознанное решение — в прошлом были проблемы, когда
из-за строгой проверки версии клиенты залипали на устаревших данных при
обрывах синхронизации. Источник истины (текущий ЛМ) важнее номера версии.
**Не убирать это условие без понимания истории вопроса.**

## Жизненный цикл: вход в игру

1. `ADDON_LOADED` → `LoadSettings()` + `CreateUI()` → восстановление
   `auction.bids`/`signups`/`dataVersions` из `SavedVariables` →
   `ApplySettings()` → `auction.fullyLoaded = true`.
2. Если к этому моменту WoW уже прислал `PLAYER_ENTERING_WORLD` (может
   случиться раньше `ADDON_LOADED`) — флаг `auction.pendingWorldEnter`
   ловит это и вызывает `HandleWorldEnter()` сразу после инициализации.
3. `HandleWorldEnter()` (`comm.lua`), через 2 сек (даём время догрузиться
   раид-ростеру):
   - если я ЛМ и есть ставки в памяти → рассылаю `SyncAllToRaid()`;
   - если я ЛМ и ставок нет → просто `"LM"` в рейд;
   - если не ЛМ → `RequestDataFromLM()` (запрашиваю данные у лутера);
   - в любом случае → `BroadcastMyVersion()` в гильдию.
4. Если версия аддона выросла с прошлого входа (`EPBossAuctionSavedLastSeenVersion`
   меньше `auction.version`) — через 2 сек показывается окно "Что нового?"
   (`ShowWhatsNewWindow` в `ui.lua`).

`GROUP_ROSTER_UPDATE`/`RAID_ROSTER_UPDATE` (в `events.lua`) переигрывает
похожую логику (кто ЛМ, нужно ли досинхронизироваться) при каждом изменении
состава пати/рейда, с debounce-таймером на 2 сек, чтобы не спамить сеть при
быстрых инвайтах.

## UI

- `auction:CreateUI()` (`ui.lua`) строит главное окно один раз при загрузке:
  слева — панель управления (дропдауны босса/предмета, поле ставки, кнопки
  ЛМ, кнопки явки), справа — `ScrollFrame` с таблицей предметов текущего
  босса.
- Строки таблицы — через пул (`auction.rowPool`), не пересоздаются на каждый
  рефреш.
- Кнопки явки (`CreateSignupButtons`/`RefreshSignupButtons`) — **не** через
  `SkinButton` из `theme.lua`, у них свой скин прямо в `ui.lua` (иначе
  конфликтует `OnLeave`-хук из `SkinButton` с подсветкой "явка отмечена").
- Дропдаун "Предмет" (`itemDropdown`) визуально скрыт (`:Hide()` сразу после
  создания) — выбор предмета происходит кликом по строке таблицы, дропдаун
  дублировал этот выбор. Код не удалён: на `auction.itemDropdown` завязаны
  вызовы `UIDropDownMenu_SetText` из обработчика клика по строке, и на сам
  фрейм заякорен `bidLabel` ("Сумма ставки:") ниже — удаление сломало бы оба
  места. Чтобы вернуть видимость — убрать `itemLabel:Hide()`/`itemDrop:Hide()`.
- Окно "Что нового?" (`ShowWhatsNewWindow`, самый низ `ui.lua`) строится один
  раз лениво (`auction.whatsNewFrame`), берёт текст из `auction.changelog`
  (`core.lua`) через `GetChangelogSince(lastSeenVersion)`.

## Attendance (посещаемость)

Вкладка видна только ЛМ и офицерам. Рейдеры ничего не хранят и вкладку не видят.

**Как данные попадают в историю.** Снимок состава рейда делается в момент
«Очистить таблицу» (после килла и раздачи лута), функция
`auction:RecordAttendance(bossName, sender)` в `attendance.lua`. Вызывается:

- у ЛМ — из `EndAuctionLocal` / `EndAuctionAllLocal` (`ui.lua`), **до** очистки,
  потому что очистка стирает явку «Хочу отдохнуть», а она попадает в снимок;
- у остальных — из `Handle_END` / `Handle_END_ALL` (`comm.lua`). Сообщения
  приходят всему рейду, поэтому офицеры записывают то же самое на своём клиенте.
  Отдельной синхронизации истории между игроками нет: у каждого свои записи, только
  за те киллы, при которых он был в рейде с загруженным аддоном.

**Что в записи:** время, босс и подземелье, состав рейда (имя → класс), и кто из
них был отмечен «Хочу отдохнуть» на этого босса.

**Защита от мусора:** запись не создаётся вне рейда, у тех, кто не ЛМ/офицер, и
при сообщении не от текущего ЛМ (`auction.lastLM`); две записи по одному боссу
ближе 15 секунд считаются дублем (у ЛМ событие приходит дважды: локальная
очистка и эхо сообщения). Хранится не больше 600 последних записей.

**Кто «офицер»** — единственное место: `auction:CanRecordAttendance()` (ЛМ, лидер
или ассистент рейда, офицер гильдии по `CanViewOfficerNote()`). Хотите другое
правило — правьте только эту функцию.

**Подсчёт.** `auction:BuildAttendanceReport(records, now, periodDays, maxColumns)` —
чистая функция без обращений к WoW API: процент считается по **киллам** за период
(был на 8 из 10 убитых), а не по дням. Ячейки: `+` в рейде, `О` в рейде, но
отмечен «Хочу отдохнуть», `-` не было. В процент входят и `+`, и `О`.

**UI.** Две вкладки в левом верхнем углу окна («Ставки» / «Attendance») и панель
на всю рабочую область (`CreateAttendancePanel`). Если доступа нет, вкладки
скрыты и окно выглядит как раньше. ПКМ по дате в шапке — удалить запись (на
случай, если очистили по ошибке).

**Не сделано (намеренно, для первой версии):** учёт по мейнам (твинки считаются
отдельными игроками), синхронизация истории между офицерами, автоматическое
определение килла по смерти босса.

## Настройки

`auction.defaults` (`core.lua`) — единственный источник дефолтов, структура:
`general` / `table` / `minimap` / `window`. При загрузке `auction.db =
MergeDefaults(EPBossAuctionSettings, auction.defaults)` — то есть **при
добавлении новой настройки просто допиши ключ в `auction.defaults`**, старым
пользователям он подставится автоматически, ничего больше делать не нужно.

Панель настроек (`options.lua`) читает/пишет `auction.db.*` напрямую;
`auction:ApplySettings()` (`core.lua`) применяет изменения к уже открытому
окну на лету.

## Как выпустить новую версию

1. Внести изменения в код.
2. В `core.lua`: поднять `auction.version` и добавить новую запись в
   `auction.changelog["x.y.z"] = { "пункт 1", "пункт 2", ... }`.
3. В `EPBossAuction.toc`: поднять `## Version:` на то же значение.
4. Залить в репозиторий.

Больше ничего делать не нужно — окно "Что нового?" и гильдейское уведомление
об обновлении сработают автоматически на основе этих двух чисел (см.
[Жизненный цикл](#жизненный-цикл-вход-в-игру)).

---

## Как добавить новую сетевую команду

1. В `comm.lua`: функция отправки (`SendAddonMessage(self.prefix,
   "ИМЯ;параметр", "КАНАЛ")`) и функция `auction:Handle_ИМЯ(rest, sender)`.
   Регистрировать отдельно не нужно — диспетчер `HandleMessage` найдёт по
   имени.
2. Добавить строку в таблицу протокола выше (и в комментарий-шапку
   `comm.lua`) — иначе следующий человек не найдёт команду в документации.
3. Если команда меняет данные, которые показываются в UI — не забыть
   обновить UI (`RequestRefresh()`/`RefreshSignupButtons()` и т.п.) и, если
   нужно, сохранить (`RequestSaveData()`).

## Известные особенности и грабли

- **`GetConfiguredItemName`/`self.itemNames`** (`core.lua`) — мёртвый код,
  наследие старой системы кастомных названий предметов (до явки на босса).
  `self.itemNames` больше нигде не заполняется, функция всегда возвращает
  `nil`. Безопасно, но можно убрать вместе с одним вызовом в
  `GetCachedItemName`.
- **`auction.lastLM` не аутентифицирован** — см. раздел про роль ЛМ выше.
  Известное ограничение, не баг.
- **`journal.lua`/`queue.lua`/`lootmaster.lua`** — если увидишь упоминания в
  старых версиях/бэкапах: это удалённые модули (журнал ставок, очередь
  токенов, окно раздачи лута с авто-списанием EP). Убраны осознанно, аддон
  сейчас — только таблица ставок, без автоматической раздачи лута.
- **Имена боссов в `auction.instances` должны в точности совпадать с ключами
  `auction.bosses`.** Не дописывайте в имя пометки вроде «(не заполнено)»: выбор
  такого босса не находит свой список предметов, и `RefreshTable` сбрасывает
  выбор. Пометка для боссов без предметов рисуется отдельно, в дропдауне
  (`ui.lua`, по пустому списку в `auction.bosses`).
- **Высота окна по умолчанию — 605** (`auction.defaults.window.height` и две
  проверки `math.max(605, ...)` в `core.lua`): при меньшей высоте низ левой
  панели (с дропдауном подземелья и кнопками явки) может обрезаться.
- **Порядок файлов в `.toc` важен** — `core.lua` должен грузиться первым
  (создаёт `auction`), `events.lua` — последним (вешает обработчик событий,
  которому нужны уже существующие функции из всех остальных файлов).
- **`UpdateScrollFrameSize` и `GetCachedItemName` определены дважды** — в
  `core.lua` и в `ui.lua`. Так как `ui.lua` грузится позже, версии из
  `ui.lua` побеждают, версии из `core.lua` — мёртвый код (помечено прямо
  в коде). Для `UpdateScrollFrameSize` реализации идентичны (просто
  копипаста), для `GetCachedItemName` — **разные** (в `ui.lua` ещё
  кэшируется иконка). Если редактируешь одну из этих функций — редактируй
  версию в `ui.lua`, иначе правка не будет иметь эффекта.

---

## Отладка

- `auction.debug = true` в `core.lua` (или чекбокс в настройках) — включает
  подробный лог через `auction:Debug(...)` в чат (серым, `[EPBA DEBUG]`).
  Почти каждая сетевая и жизненно-цикловая функция логирует свои шаги —
  первое, что смотреть при "почему не работает".
- `/epgpfind` — сканирует `_G` в поисках EPGP-подобных таблиц, полезно при
  проблемах с получением EP на новом сервере/версии EPGP.

## Слэш-команды

| Команда | Действие |
|---|---|
| `/epba` | открыть/закрыть главное окно |
| `/epbasave` | принудительно сохранить данные |
| `/epbaupdate` | принудительно обновить EP из EPGP |
| `/epbazoom+` / `/epbazoom-` / `/epbazoomreset` | масштаб окна |
| `/epbaoptions` | открыть панель настроек |
| `/epbaoffspec <0.1-1.0>` | коэффициент офф-спека (только ЛМ) |
| `/epgpfind` | отладочный поиск EPGP-аддона в `_G` |
