# EPBossAuction — инструкция для разработчика

Гильдейский аддон для WotLK 3.3.5a: рейдеры делают ставки EP на лут по EPGP,
Loot Master видит список ставок по каждому предмету каждого босса и раздаёт
лут: окно выдачи добычи (`lootmaster.lua`) выдаёт предмет победителю через
мастер-лут и по кнопке списывает EP по его ставке. Сами ставки и таблица
по-прежнему не раздают лут автоматически — выдача и списание всегда по
кнопке ЛМ.

Этот файл — не техдокументация по каждой строчке (это делают комментарии в
самом коде), а карта: что где искать, как это всё связано и на что не
наступить при доработке.

## Файлы и их зоны ответственности

| Файл | Что внутри |
|---|---|
| `core.lua` | Глобальная таблица `EPBossAuction` (везде далее — `auction`). Список боссов/предметов (`auction.bosses`), дефолтные настройки (`auction.defaults`), явка на босса, версия аддона (читается из `## Version:` в toc), утилиты (`CompareVersions`, `FormatNumber`, `DeepCopy`, `MergeDefaults`), загрузка/сохранение SavedVariables. |
| `changelog.lua` | Список изменений по версиям (`auction.changelog`) для окна "Что нового?". Только текст, без логики. |
| `comm.lua` | Весь сетевой протокол: отправка (`SendAddonMessage`) и приём (`Handle_*`). См. таблицу команд в шапке файла и ниже в этой инструкции. |
| `ui.lua` | Главное окно, таблица предметов, кнопки явки, окно "Что нового?", слэш-команды. Не трогает сеть напрямую — вызывает функции из `comm.lua`. |
| `events.lua` | Единственная точка входа: один фрейм, один `OnEvent`, реагирует на `ADDON_LOADED`, `PLAYER_ENTERING_WORLD`, `CHAT_MSG_ADDON`, `GROUP_ROSTER_UPDATE`/`RAID_ROSTER_UPDATE`, `PLAYER_LOGOUT`, `EPGP_UPDATE`. |
| `epgp.lua` | Мост к внешнему EPGP-аддону (EPGP / EPGP_Auction / CEPGP / EPGPCore) — получение EP игрока, с резолвом твинк → мейн. |
| `theme.lua` | Палитра + хелперы `SkinPanel`/`SkinButton`/`SkinInput`/`SkinCheckbox`/`SkinDropdown`/`SkinScrollBar` для единого тёмного стиля. |
| `options.lua` | Панель настроек (Interface Options → EPBossAuction). |
| `minimap.lua` | Кнопка на миникарте. |
| `help.lua` | Окно «Справка» (обучение): страницы в `BuildHelpPages`, листание «Назад»/«Далее». Страница про Attendance/Резерв — только при `HasAttendanceAccess()`; страница про окно добычи — при `IsLootMaster()` или `HasAttendanceAccess()`. Новым пользователям показывается сам один раз (флаг `EPBossAuctionSavedHelpSeen`, логика в `events.lua`). **При смене названий кнопок или поведения интерфейса — править текст здесь.** Страница «Если что-то не работает» (про диагностику) — для всех; при изменении вкладок/команд diag.lua правьте и её. |
| `contacts.lua` | Окно «Сообщить о проблеме» (`/epba bug`): ссылка на GitHub Issues и контакт в Discord (таблица `auction.contacts` в шапке файла — поменять там), строка диагностики (`GetDiagnosticsString`). Поля только для копирования (Ctrl+C). |
| `diag.lua` | Диагностика: журнал, перехват ошибок Lua, трассировка сети, проверки целостности, опрос рейда (DPING/DPONG), окно `/epba diag`. Грузится после `contacts.lua`. |
| `attendance.lua` | Посещаемость (только для тех, кто может редактировать офицерскую заметку): данные и логика — доступ, запись снимков состава рейда (автоматическая и ручная), удаление/очистка, слияние, подсчёт (`BuildAttendanceReport` и сводки — чистые функции), текст отчёта. |
| `attendance_sync.lua` | Синхронизация истории посещаемости между офицерами (`ATT_REQ`/`ATT_REC`/`ATT_DONE`): сериализация, нарезка на сообщения, очередь отправки. |
| `attendance_ui.lua` | Вкладка Attendance: вкладки главного окна, панель (тулбар, три вида таблицы), окно с текстом отчёта. |
| `reserve.lua` | Резерв предметов (проданных заранее покупателям не из гильдии): данные, проверка `IsReserved`, рассылка публичного списка ЛМ → рейд, синхронизация между офицерами. Доступ — как у Attendance. |
| `reserve_ui.lua` | Вкладка «Резерв»: выбор босса, список предметов, «+»/«-», заметка о покупателе, вставка ссылок. |
| `stats.lua` | Статистика выдач и ЕП: журнал (`StatsAddRecord`, `LootJournalAddMass`, очистка), чистые функции подсчёта (`BuildStatsPlayers/Items/Bosses/Totals/BossList`), текст отчёта. Доступ — `HasStatsAccess` (= Attendance). |
| `stats_ui.lua` | Вкладка «Статистика»: панель, три вида таблицы, тултипы, окно отчёта. |
| `lootmaster.lua` | Окно выдачи добычи для ЛМ: выпавшие предметы, топ ставок, «Выдать»/«Выдать себе»/«Списать ЕП», массовое начисление ЕП за босса, журнал выдач. Своя регистрация событий (`LOOT_OPENED` и др.) и команда `/epbaloot`. Подробности — в разделе «Окно выдачи добычи». |
| `EPBossAuction.toc` | Манифест: версия, список файлов (порядок загрузки важен!), `SavedVariables`. |

**Правило**: данные — в `core.lua`, сеть — в `comm.lua`, отрисовка — в `ui.lua`.
Если добавляешь фичу и не понимаешь, в какой файл её класть — скорее всего,
она разъезжается на три части (структура данных / рассылка / кнопка), и это
нормально, так устроен весь остальной код.

## Данные: что и где хранится

Всё висит прямо на таблице `auction` (не через `self.db`, кроме настроек —
см. ниже), заполняется в `events.lua` при `ADDON_LOADED` из `SavedVariables`:

| Поле | Что это | SavedVariable |
|---|---|---|
| `auction.bids[boss][itemID]` | список `{player, amount, isOffspec}` — текущие ставки | `EPBossAuctionSavedBids` |
| `auction.signups[boss][category]` | `{[playerName] = true}` — явка (`fight`/`rest`; список — `auction.SIGNUP_CATEGORIES`) | `EPBossAuctionSavedSignups` |
| `auction.dataVersions[boss:itemID]` | счётчик версии данных (у ЛМ растёт при каждой ставке) | `EPBossAuctionSavedVersions` |
| `auction.lastVersions[boss:itemID]` | последняя версия, которую **я** применил из SYNC | не сохраняется (сбрасывается при входе) |
| `auction.attendance` | список записей посещаемости, по возрастанию времени (формат — в шапке `attendance.lua`) | `EPBossAuctionSavedAttendance` |
| `auction.attendanceMeta` | метки удаления/очистки (`clearedBefore`, `deleted`), чтобы синхронизация не вернула удалённое | `EPBossAuctionSavedAttendanceMeta` |
| `auction.reserves[boss][itemID]` | `{qty, note, t, by}` — резерв (только у тех, у кого есть доступ; `qty = 0` — «надгробие» для синхронизации) | `EPBossAuctionSavedReserves` |
| `auction.reservePublic[boss][itemID]` | `qty` — публичная копия резерва от ЛМ (без заметок), у остальных игроков | не сохраняется |
| `auction.db` | настройки (см. `auction.defaults` в `core.lua`); внутри `db.lootmaster` — позиция окна добычи и последняя сумма «за босса» по боссам (создаётся лениво, в `defaults` не описано) | `EPBossAuctionSettings` |
| `auction.lootEntries` | записи окна добычи — по одной на слот (формат — в шапке `lootmaster.lua`) | не сохраняется |
| `EPBossAuctionSavedLootLog` | журнал выдач и массовых начислений ЛМ, последние 2000 записей (формат — в шапке `stats.lua`); источник вкладки «Статистика» | `EPBossAuctionSavedLootLog` |
| `auction.bidsLocked` | заблокированы ли ставки | `EPBossAuctionBidsLocked` |

`dataVersions` и `lastVersions` — разные вещи, их легко перепутать по
названию. Комментарий над этим блоком в `core.lua` объясняет разницу
подробнее.

`auction.bosses[bossName]` — статический список `itemID` по каждому боссу,
правится руками в `core.lua`. Если сервер меняет лут-таблицу боссов — тут и
поправлять.

`auction.instances[instanceName]` — группировка боссов по подземельям (для
двухуровневого меню "Подземелье" → "Босс"). `auction.bossToInstance[bossName]` — обратный
индекс, нужен только для восстановления выбора при входе (`events.lua`).
Важно: сами данные (ставки/явка/версии/сеть) как хранились, так и хранятся по
`bossName`, подземелье в эти ключи не подмешивается — оно чисто для UI-группировки,
ничего в протоколе/SavedVariables из-за этого не менялось.

## Роль Loot Master (ЛМ)

`auction:IsLootMaster()` (`core.lua`) — **не** сетевой статус, а прямая
проверка через `GetLootMethod()`/раид-ростер: правда ли этот клиент сейчас
мастер-лут в понимании самого WoW. Это нельзя подделать по сети — кто угодно
может разослать сообщение `"LM"`, но `IsLootMaster()` у него всё равно вернёт
`false`, если он не мастер-лут на самом деле.

А вот `auction.lastLM` (от кого принимать `SYNC`) — **это** устанавливается
по сетевым сообщениям (`Handle_LM`/`Handle_LM_RESPONSE`) без проверки. Так и
задумано (см. следующий блок про `Handle_SYNC`), но если когда-нибудь
понадобится защита от подмены ЛМ по сети — копать нужно именно здесь, а не в
`IsLootMaster()`.

## Сетевой протокол

Все сообщения — через `SendAddonMessage(auction.prefix, ...)`, формат
`"КОМАНДА;параметр1;параметр2;..."`. Входящие приходят в `events.lua`
(`CHAT_MSG_ADDON`) → `auction:HandleMessage(msg, sender)` в `comm.lua`, которая
по первому слову до `;` находит и вызывает `auction:Handle_<КОМАНДА>(rest, sender)`.

**Чтобы добавить новую команду, ничего регистрировать не нужно** — просто
написать функцию `auction:Handle_ИМЯ(rest, sender)`, диспетчер найдёт её сам.

| Команда | Канал | Кто → кому | Зачем |
|---|---|---|---|
| `LM` | RAID | ЛМ → рейд | "Я лутер" |
| `LM_REQUEST` | WHISPER | игрок → ЛМ | "Кто у нас лутер?" |
| `LM_RESPONSE` | WHISPER | ЛМ → игрок | ответ на `LM_REQUEST` |
| `HELLO` | WHISPER | игрок → ЛМ | "Пришли данные по боссу X" (или без параметра — по всем) |
| `HELLO_ACK` | WHISPER | ЛМ → игрок | подтверждение получения `HELLO` |
| `CHECK_VERSION` | WHISPER | игрок → ЛМ | "Какие у тебя версии данных?" |
| `VERSIONS` | WHISPER | ЛМ → игрок | ответ на `CHECK_VERSION` |
| `BID` | WHISPER | игрок → ЛМ | ставка (`amount = 0` = отказ от ставки) |
| `BIDOK` | WHISPER | ЛМ → игрок | ставка принята |
| `TOOLOW` | WHISPER | ЛМ → игрок | ставка меньше минимальной |
| `SYNC2` | RAID/WHISPER | ЛМ → все | ставки по предмету + версия: `SYNC2;босс(№ в bossOrder);itemID;версия;ник:сумма[*],…[;невлезло]`. Влезают самые крупные ставки (лимит 255 байт). Старый `SYNC` с 3.5.2 только принимается (`Handle_SYNC`), не отправляется |
| `SYNC_COMPLETE` | RAID/WHISPER | ЛМ → все | "синхронизация завершена" |
| `LOCK` | RAID | ЛМ → рейд | блокировка/разблокировка ставок |
| `LOCKED` | WHISPER | ЛМ → игрок | "ставки сейчас заблокированы" (в ответ на BID во время лока) |
| `END` | RAID | ЛМ → рейд | очистка ставок+явки по одному боссу (ПКМ). |
| `END_ALL` | RAID | ЛМ → рейд | очистка ставок+явки по всем боссам (ЛКМ; посещаемость не пишется) |
| `SIGNUP` | RAID | любой → рейд | явка (хочу бить/отдохнуть) |
| `MY_VERSION` | **GUILD** | любой → гильдия | версия аддона (для уведомления об обновлении) |
| `ATT_REQ` | **GUILD** | офицер → гильдия | запрос синхронизации посещаемости: ключи уже имеющихся записей, часть i из n |
| `ATT_REC` | WHISPER | офицер → запросивший | кусок одной записи посещаемости (ответ на `ATT_REQ`) |
| `ATT_DONE` | WHISPER | офицер → запросивший | «закончил отвечать, прислал N записей» |
| `OFFSPEC_MULT` | RAID | ЛМ → рейд | новый коэффициент офф-спека |
| `RES` / `RES_END` | RAID | ЛМ → рейд | публичный список резерва: записи, затем итог с числом записей (применяется только целиком) |
| `RES_ONE` | RAID | ЛМ → рейд | одиночное изменение резерва (`qty = 0` — снято) |
| `RESERVED` | WHISPER | ЛМ → игрок | ставка отклонена: предмет в резерве |
| `RES_UPD` | **GUILD** | офицер → офицеры | правка одной записи резерва (live) |
| `RES_REQ` / `RES_REC` / `RES_DONE` | **GUILD** / WHISPER | офицер ↔ офицер | pull-синхронизация резерва, как `ATT_*` |

Обрати внимание: на канале `GUILD` только `MY_VERSION`, `ATT_REQ`, `RES_UPD` и `RES_REQ`, все остальные —
`RAID`/`WHISPER`. Это осознанно: аддон гильдейский, а не только рейдовый, уведомление
об обновлении должно доходить до всех в гильдии, а офицеры синхронизируют историю
посещаемости и вне рейда.

### Важный неочевидный момент: `Handle_SYNC`

```lua
if version > lastVersion or senderIsLM then
```

Выглядит как баг (версия по факту не проверяется, если сообщение пришло от
текущего ЛМ), но это осознанное решение — в прошлом были проблемы, когда
из-за строгой проверки версии клиенты залипали на устаревших данных при
обрывах синхронизации. Источник истины (текущий ЛМ) важнее номера версии.
**Не убирать это условие без понимания истории вопроса.**

## Жизненный цикл: вход в игру

1. `ADDON_LOADED` → `LoadSettings()` + `CreateUI()` → восстановление
   `auction.bids`/`signups`/`dataVersions` из `SavedVariables` →
   `ApplySettings()` → `auction.fullyLoaded = true`.
2. Если к этому моменту WoW уже прислал `PLAYER_ENTERING_WORLD` (может
   случиться раньше `ADDON_LOADED`) — флаг `auction.pendingWorldEnter`
   ловит это и вызывает `HandleWorldEnter()` сразу после инициализации.
3. `HandleWorldEnter()` (`comm.lua`), через 2 сек (даём время догрузиться
   раид-ростеру):
   - если я ЛМ и есть ставки в памяти → рассылаю `SyncAllToRaid()`;
   - если я ЛМ и ставок нет → просто `"LM"` в рейд;
   - если не ЛМ → `RequestDataFromLM()` (запрашиваю данные у лутера);
   - в любом случае → `BroadcastMyVersion()` в гильдию.
4. Если версия аддона выросла с прошлого входа (`EPBossAuctionSavedLastSeenVersion`
   меньше `auction.version`) — через 2 сек показывается окно "Что нового?"
   (`ShowWhatsNewWindow` в `ui.lua`).

`GROUP_ROSTER_UPDATE`/`RAID_ROSTER_UPDATE` (в `events.lua`) переигрывает
похожую логику (кто ЛМ, нужно ли досинхронизироваться) при каждом изменении
состава пати/рейда, с debounce-таймером на 2 сек, чтобы не спамить сеть при
быстрых инвайтах.

## UI

- `auction:CreateUI()` (`ui.lua`) строит главное окно один раз при загрузке:
  слева — панель управления (меню босса, поле ставки, кнопки
  ЛМ, кнопки явки), справа — `ScrollFrame` с таблицей предметов текущего
  босса.
- Строки таблицы — через пул (`auction.rowPool`), не пересоздаются на каждый
  рефреш.
- Кнопки явки (`CreateSignupButtons`/`RefreshSignupButtons`) — **не** через
  `SkinButton` из `theme.lua`, у них свой скин прямо в `ui.lua` (иначе
  конфликтует `OnLeave`-хук из `SkinButton` с подсветкой "явка отмечена").
- Выбор босса — одно двухуровневое меню `EPBossDropdown` (`auction.bossDropdown`):
  первый уровень — подземелья (`auction.instanceOrder`, `hasArrow`), второй — боссы
  подземелья из `UIDROPDOWNMENU_MENU_VALUE` (так же сделано в Attendance и «Резерве»).
  При выборе босса ставятся `selectedInstance`/`selectedBoss`, сбрасывается
  `selectedItem`. Подпись меню обновляет `auction:UpdateBossDropdownText()` (в конце
  `ui.lua`; её зовут выбор босса, восстановление при входе в `events.lua` и
  `comm.lua`). Отдельного списка подземелий нет: `auction.instanceDropdown` всегда `nil`.
- Дропдаун "Предмет" (`itemDropdown`) визуально скрыт (`:Hide()` сразу после
  создания) — выбор предмета происходит кликом по строке таблицы, дропдаун
  дублировал этот выбор. Код не удалён: на `auction.itemDropdown` завязаны
  вызовы `UIDropDownMenu_SetText` из обработчика клика по строке и из
  `reserve.lua`. На раскладку он не влияет: `bidLabel` ("Сумма ставки:")
  заякорен на меню босса, а не на него. Чтобы вернуть видимость — убрать
  `itemLabel:Hide()`/`itemDrop:Hide()` и заякорить `bidLabel` обратно на `itemDrop`.
- Окно "Что нового?" (`ShowWhatsNewWindow`, самый низ `ui.lua`) строится один
  раз лениво (`auction.whatsNewFrame`), берёт текст из `auction.changelog`
  (`changelog.lua`) через `GetChangelogVersions()`.

## Attendance (посещаемость)

Вкладка, запись и ответы на синхронизацию доступны только тем, кто может **редактировать
офицерскую заметку** гильдии (`CanEditOfficerNote()`). Остальные ничего не хранят и
вкладку не видят.
Код разделён на три файла: данные и логика (`attendance.lua`), синхронизация
(`attendance_sync.lua`), интерфейс (`attendance_ui.lua`).

**Как данные попадают в историю.** Только вручную: выпадающий список «Записать килл»
на вкладке (подземелье → босс, с подтверждением, нужно быть в рейде). Очистка таблицы
(ПКМ и ЛКМ) посещаемость **не** пишет. Снимок делает `auction:RecordAttendanceManual`
→ `AddAttendanceRecord(bossName, true)` в `attendance.lua`: время, босс, подземелье, состав
рейда с классами, отмеченные «Хочу отдохнуть», мейны твинков. Кнопка «Записать килл» не
требует, чтобы вы были ЛМ.

**Босс обязателен**: неизвестное имя (`auction.bosses`) запись не создаёт. У каждой записи
есть уникальный `id` (`"время:случайное"` в hex; у старых записей — `"время:хэш_босса"`,
см. `AttendanceKey`). Одним киллом считаются записи, у которых совпадает босс, время
различается не больше чем на `ATTENDANCE_SAME_KILL_SECONDS` (3 часа) и состав рейда
совпадает не меньше чем на `ATTENDANCE_SAME_ROSTER_RATIO` (60% от меньшего состава) —
`IsSameKill`. Это отсекает повторные клики и дубли от другого офицера, но не склеивает
настоящие киллы одного босса разными составами (основа и твинк-рейд). При слиянии чужой
`id` запоминается в `rec.alt` («двойник»), чтобы синхронизация не присылала этот килл
снова. Запись не создаётся вне рейда и без доступа к Attendance. Хранится не больше 600
записей. Историю у каждого
офицера пополняет и выравнивает синхронизация (см. ниже).

**Правило доступа** — одно место: `auction:CanRecordAttendance()` = состоит в гильдии
и `CanEditOfficerNote()`. `HasAttendanceAccess()` возвращает то же самое. Статус ЛМ или
рейд-ассистента и нахождение в рейде не нужны, поэтому историю видно и вне рейда.
Если права на заметки потеряны, вкладка скрывается (накопленная история остаётся на
диске, но недоступна). Хотите другое правило — правьте только эту функцию.

**Мейны (твинки).** При записи для каждого игрока спрашивается EPGP-аддон
(`auction:GetMainName(имя)` в `epgp.lua`, кэш 5 минут) и мейны твинков кладутся в
запись (`rec.mains`). Чекбокс «По мейнам» (`auction.db.attendance.byMain`, по умолчанию
включён) считает твинка и мейна одним человеком: килл с обоими — один раз, килл только
с твинком — засчитан мейну; «отдыхом» считается, только если отдыхают все персонажи.
Для старых записей и записей, пришедших от офицера без EPGP, мейн спрашивается у EPGP
на лету (`GetAttendanceResolver`). Без EPGP-аддона режим ничего не меняет.

**Синхронизация между офицерами** (`attendance_sync.lua`). Кнопка «Синхронизировать»
и один автозапуск за сессию (через 25 секунд после входа в мир, из `HandleWorldEnter`).
Запрашивающий шлёт в `GUILD` список ключей своих записей за 60 дней (`ATT_REQ`,
ключи — `id` записей и их «двойников» `alt`); офицеры с доступом отвечают по `WHISPER` записями, которых в
списке нет (`ATT_REC`, затем `ATT_DONE`). Сообщения 3.3.5a ограничены 255 байтами,
поэтому запись режется на куски (`SplitUtf8` не рвёт русские буквы), отправка идёт
очередью раз в 0.2 секунды. Принятая запись проходит проверку (известный босс,
разумное время, не больше 60 игроков) и сливается (`MergeAttendanceRecord`): при
совпадении килла остаётся локальная запись. Удалённое вручную и очищенное назад не
возвращается: `attendanceMeta` хранит метки (`deleted`, `clearedBefore`).
Ограничения: любой гильдеец с аддоном может запросить историю (клиент не может
проверить, что запрашивающий — офицер), данные — только имена и классы; одному
запросившему отвечаем не чаще раза в 20 секунд.

**Периоды и рейдовые недели.** Период вкладки — выпадающий список: 7 дней / 30 дней / всё
время либо рейдовая неделя (`auction.attendanceWeek`). Неделя идёт с четверга: номер —
`AttendanceWeek(t)`, начало — `AttendanceWeekStart(week)`, момент сброса в течение суток
задаёт `ATTENDANCE_RESET_OFFSET` (3 ч после 00:00 UTC = 06:00 МСК). `GetAttendancePeriod()`
возвращает `{ label, range }`; `range` — число дней либо `{ from, to }` для недели, и это
значение передаётся в `Build*`. Число колонок-дат в таблице игроков зависит от ширины окна
(`GetAttendanceVisibleColumns`, не больше `ATTENDANCE_COLUMNS`).

**Подсчёт** — чистые функции без обращений к WoW API (кроме `date`), их проверяют
тестами вне игры:
- `BuildAttendanceReport(records, now, periodDays, maxColumns, bossFilter, resolveMain)` —
  таблица игроков; процент считается по **киллам** за период (был на 8 из 10 убитых),
  но **только начиная с первого появления игрока в истории** (`entry.firstT`; ищется по
  всей истории, без фильтров периода/босса, при подсчёте по мейнам — по самому раннему
  появлению любого из персонажей). Новичок не штрафуется за киллы, на которых его ещё не
  было: `entry.total` — знаменатель у каждого игрока свой. Ячейки: `+` в рейде, `О` в
  рейде, но отмечен «Хочу отдохнуть», `-` не было; пустая ячейка — килл был до первого
  появления игрока (в процент не входит); в процент входят и `+`, и `О`. Также
  возвращается `firstSeen` (имя → время);
- `BuildAttendanceBossList` — боссы для фильтра (порядок как в аддоне);
- `BuildBossSummary` — по боссам: киллов, средний состав, уникальные игроки, последний килл;
- `BuildDaySummary` — по рейд-дням: киллов, уникальные игроки, средний состав, боссы;
- `BuildAttendanceReportText` — CSV с разделителем `;` под текущий вид.

**UI.** Две вкладки в левом верхнем углу окна («Ставки» / «Attendance») и панель на всю
рабочую область. Тулбар в два ряда: Период | Вид (Игроки / Боссы / Дни) | фильтр «Босс»;
«Записать килл» | Синхронизировать | Отчёт | Очистить | «По мейнам». Виды: «Игроки» —
таблица с колонками-датами; «Боссы» — сводка (клик по строке открывает посещаемость по
этому боссу); «Дни» — по рейд-дням. Фильтр «Босс» меняет колонки, проценты и счётчик
(`bossFilter`), сбрасывается сам, если босса нет ни в одной записи. ПКМ по дате в шапке —
удалить запись; «Очистить» удаляет всю историю **на этом клиенте** (с подтверждением);
«Отчёт» открывает окно с выделенным текстом для Ctrl+C. Если доступа нет, вкладки
скрыты и окно выглядит как раньше.

**Тултип ставок.** При наличии доступа в тултипе ставок рядом с EP показывается посещаемость
игрока за 30 дней (`GetAttendancePercentFor`, кэш до изменения истории, смены режима
«по мейнам» или 60 секунд). Процент — от первого появления игрока; у игрока, которого ещё ни разу не было в
истории, посещаемость в тултипе не показывается.

**Не сделано:** автоматическое определение килла по смерти босса.

## Резерв предметов

Иногда рейд ведут под продажу предметов за золото покупателям не из гильдии; что им нужно,
оговорено заранее. Такие предметы помечаются «резервом», и на них нельзя делать ставки.
Вкладка «Резерв» и правка списка доступны тем же, кто видит Attendance (`HasReserveAccess` →
`HasAttendanceAccess`, правило доступа по-прежнему в одном месте).

**Данные.** `auction.reserves[boss][itemID] = { qty, note, t, by }`. `qty > 0` закрывает предмет
для ставок целиком (аддон не знает, сколько копий выпало); `qty` — сколько копий продано, кнопка «−»
на вкладке уменьшает его, когда предмет выдан покупателю, на 0 предмет снова открыт. `qty = 0` хранится
как «надгробие» `RESERVE_TOMBSTONE_DAYS` (30) дней, чтобы снятие дошло до других офицеров. Предел —
`RESERVE_MAX_ENTRIES` (250) записей. Резерв **не** чистится «Очистить таблицу» (ни ЛКМ, ни ПКМ).

**Два уровня защиты.**
1. `Handle_BID` на ЛМ (comm.lua) вызывает `IsReserved` и на ставку > 0 отвечает `RESERVED`. Это
   жёсткая защита: не зависит от версии аддона и клиента игрока. Снять свою ставку (`amount = 0`) можно всегда.
2. Остальные клиенты видят резерв в таблице (строка затемнена, надпись «Резерв — ставки закрыты»,
   выбрать предмет и отправить ставку нельзя: `ApplyReserveMark`, проверки в `CreateRowTemplate` и
   `SendBidLocal` в ui.lua). Это удобство, не безопасность.

**Кто что знает.** Тот, у кого есть доступ (включая ЛМ), читает резерв из своего `auction.reserves`.
Остальные — из `auction.reservePublic`, который присылает ЛМ: `RES…RES_END` целиком (после входа в рейд
или смены ЛМ, склеивается таймером `QueueReserveBroadcast`) и `RES_ONE` по ходу правок. Принимаются только
от `auction.lastLM`. Неполный список (потерялись сообщения) отбрасывается, а `RESERVED` «лечит» публичный список.
Заметки о покупателях в публичный список не попадают.

**ЛМ обязан иметь доступ.** Публичный список строится из вкладки ЛМ. ЛМ без доступа к «Резерву» не сможет
ни блокировать ставки, ни рассылать список: `OnBecameLootMaster` (вызывается из events.lua) один раз за сессию
пишет об этом в чат.

**Синхронизация офицеров** — по образцу Attendance, поверх той же очереди `AttQueueSend`: live-правка `RES_UPD`
и pull `RES_REQ/RES_REC/RES_DONE` (дайджест `хэшБосса:itemID:t`); при расхождении побеждает запись с большим
`t` (`MergeReserveEntry`). Автозапуск — один раз за сессию через 30 с после входа (`ScheduleReserveAutoSync`,
из `HandleWorldEnter`) и при становлении ЛМ. Ограничения те же, что у Attendance: GUILD-сообщения видит любой
гильдеец с аддоном (заметка о покупателе ≤ 30 символов идёт открыто — не пишите её, если это важно), автор записи (`by`)
берётся из имени отправителя.

**Вкладка.** Клик по предмету — резерв вкл/выкл; «+»/«−» — копии; поле справа — заметка (Enter или уход из поля);
«x» — снять. Вид «босс» — все предметы выбранного босса, «все резервы» — только зарезервированные. В поле
над таблицей можно вставить Shift+кликом ссылки на предметы (из чата) или набрать id: предмет, который
есть у нескольких боссов, резервируется у выбранного на вкладке, а если там его нет — у всех. Хелперы стиля
(`MakeButton`, `MakeDropdown`, …) берутся из `auction.uiHelpers`, который экспортирует attendance_ui.lua.

## Статистика

Вкладка «Статистика» (четвёртая квадратная кнопка слева от окна; доступ как у Attendance). Данные — журнал
`EPBossAuctionSavedLootLog`; формат записей описан в шапке `stats.lua`:
- выдача (`kind = "item"`): `id, t, lm, boss, itemID, winner, bid, offspec, bids, charged, chargedAmount, main`
  (пишет `LootJournalAdd` при выдаче, поля списания дописывает `LootDoCharge`);
- массовое начисление (`kind = "mass"`): `id, t, lm, boss, amount, n` (пишет `LootDoMass`). У записей до 3.6.0 нет `id`/`kind`/`lm` —
  подсчёт на них не опирается (`kind == nil` = выдача).

Виды: «Игроки» (предметов, ЕП списано, средняя ставка, офф-спек, последняя выдача), «Выдачи» (список, сначала новые), «Боссы»
(выдачи, ЕП, начислено рейду). Период и фильтр по боссу, «По мейнам» (`db.stats.byMain`): твинк считается с мейном; мейн берётся из
записи (`rec.main`, фиксируется при списании) или у EPGP (`GetStatsResolver`). «Потрачено» = только списанный ЕП, выдачи без
списания помечаются «*». Подсчёт — чистые функции (проверяются вне игры); UI только рисует результат.

**Ограничения.** Журнал ведёт клиент ЛМ; предметы, взятые мимо окна добычи EPBA, в него не попадают. У остальных офицеров журнал
пуст — синхронизации пока нет (по образцу Attendance/Резерва её можно добавить: для этого у записей есть `id`). «Очистить» удаляет журнал
на этом клиенте. Хранится не больше `STATS_MAX_RECORDS` (2000).

## Окно выдачи добычи

`lootmaster.lua`. Окно появляется **только** у ЛМ (`IsLootMaster()`), в рейде (`GetNumRaidMembers() > 0`),
по событию `LOOT_OPENED`, если среди слотов есть подходящие предметы: качество не ниже `LOOT_MIN_QUALITY`
(эпик) или предмет есть в `auction.bosses`, не ниже порога мастер-лута и не в `auction.LOOT_IGNORED_ITEMS`.
Стандартное окно добычи не трогается — оно остаётся запасным путём. Остальным игрокам файл ничего не делает.

**Снимок посещаемости.** Кнопка «Создать снимок» в шапке окна (`LootSnapshot`) вызывает `RecordAttendanceManual(lootBoss)` из `attendance.lua`: записывает состав рейда как килл выбранного босса (дубль за 5 минут блокируется, право — как у Attendance). В тестовом режиме ничего не пишет.

**Записи.** Одна запись на слот (`auction.lootEntries`), а не на `itemID`: так две копии одного предмета не
делят состояние. Статусы: `open` → `giving` → `given` → `charged`. Победитель по умолчанию — первый по ставке,
не занятый другой копией того же предмета; клик по строке ставки переопределяет выбор. Босс записи берётся из
обратного индекса «предмет → босс» (лут боссов уникален); общий босс окна — по большинству выпавших предметов
(`DetectBoss`), его можно поправить в дропдауне, он нужен для причины массового начисления и для предметов,
которых нет в таблицах.

**Выдача.** `LootGive`: проверяет, что слот всё ещё содержит тот же предмет, читает кандидатов
(`GetMasterLootCandidate(i)`), вызывает `GiveMasterLoot(slot, index)`. Статус `given` ставится **только** по
`LOOT_SLOT_CLEARED`. Если слот не очистился за `GIVE_TIMEOUT` (4 с) — запись возвращается в `open` с красной
пометкой (обычно: полная сумка получателя или игрок далеко); если очистка пришла с опозданием (до
`LATE_CLEAR_WINDOW`) — всё равно считается выдачей. Если слот очистился вне аддона (предмет взяли через
стандартное окно) — запись удаляется.

**Списание.** `LootConfirmCharge` → подтверждение → `LootDoCharge`: `EPGP:IncEPBy(имя, причина, -сумма)` под
`pcall`, предварительно `CanIncEPBy(причина, -сумма)`. Сумма по умолчанию = ставка победителя, её можно править в
поле; пока победитель не менялся, ручная правка не затирается. Успех — только если `IncEPBy` вернул строку (имя
мейна): `nil` значит «EPGP не знает такого игрока». EPGP начисляет и списывает ЕП **мейну**, поэтому твинк,
получивший предмет, платит с мейна. После успеха ставка победителя снимается у всех через
`ApplyBidChange(..., 0)` (она сама рассылает `SYNC`). Кнопка «Списать» срабатывает один раз на запись.

**Массовое начисление.** `LootConfirmMass` → `LootDoMass`: `EPGP:IncMassEPBy(причина = имя босса, сумма)`;
получатели — «список награждения» самого EPGP (рейд + выбранные в окне EPGP). Последняя сумма запоминается по
боссу в `db.lootmaster.bossEP`; дефолты можно задать в `auction.LOOT_BOSS_EP`. Повторное начисление за того же
босса в течение `MASS_REPEAT_SECONDS` (30 мин) только предупреждает, не блокирует.

**Окно живёт дольше добычи.** После выдачи последнего предмета Blizzard закрывает окно добычи (`LOOT_CLOSED`),
но записи `given` остаются, и окно не прячется, пока их не спишут. Закрытие кнопкой «x» убирает только уже
списанные записи; выданные-но-не-списанные переживают закрытие и следующее открытие добычи. Окно намеренно не
добавлено в `UISpecialFrames`, чтобы Esc не закрывал его посреди выдачи.

**Журнал.** При успешной выдаче `LootJournalAdd` пишет в `EPBossAuctionSavedLootLog` запись
`{t, boss, itemID, winner, bid, offspec, bids, charged}` (через `StatsAddRecord` из `stats.lua`: id, ЛМ, обрезка до 2000); при списании к ней добавляются
`chargedAmount` и `main`; массовое начисление пишется отдельной записью `kind = "mass"`. Это единственное место, где
хранится «кто что получил» (разбор — в разделе «Статистика») — таблица ставок после «Очистить таблицу» ничего не помнит. Тестовый режим
в журнал не пишет.

**Тест.** `/epbaloot test` строит окно из первых предметов выбранного в главном окне босса: выдача и списание
только имитируются, в игру и EPGP ничего не пишется. Это основной способ проверить интерфейс без рейда.

**Грабли.**
- В 3.3.5a `GetMasterLootCandidate` принимает **один** аргумент — индекс кандидата (форма «слот, индекс» из
  поздних версий здесь не работает). Индексы 1..40 перебираются без остановки на первом `nil` — пропуски нормальны.
- Порядок аргументов EPGP: `IncEPBy(name, reason, amount)`, `IncMassEPBy(reason, amount)`; для списания
  `amount` отрицательный (на сервере это разрешено). Прежний `lootmaster.lua` путал порядок.
- Победителя можно выбрать только среди сделавших ставку; остальным выдаётся через стандартное окно.
- Подтверждение привязки (BoP) при `GiveMasterLoot` на сервере не проверялось — если Sirus покажет свой запрос,
  его придётся нажимать вручную.

## Настройки

`auction.defaults` (`core.lua`) — единственный источник дефолтов, структура:
`general` / `table` / `minimap` / `window`. При загрузке `auction.db =
MergeDefaults(EPBossAuctionSettings, auction.defaults)` — то есть **при
добавлении новой настройки просто допиши ключ в `auction.defaults`**, старым
пользователям он подставится автоматически, ничего больше делать не нужно.

Панель настроек (`options.lua`) читает/пишет `auction.db.*` напрямую;
`auction:ApplySettings()` (`core.lua`) применяет изменения к уже открытому
окну на лету.

## Как выпустить новую версию

1. Внести изменения в код.
2. В `EPBossAuction.toc`: поднять `## Version:`. Это единственное место с номером
   версии: `core.lua` читает его через `GetAddOnMetadata` (`auction.version`).
3. В `changelog.lua`: добавить в конец новую запись
   `auction.changelog["x.y.z"] = { "пункт 1", "пункт 2", ... }` с тем же номером.
4. Залить в репозиторий.

Больше ничего делать не нужно — окно "Что нового?" и гильдейское уведомление
об обновлении сработают автоматически на основе номера версии в toc и записи в changelog (см.
[Жизненный цикл](#жизненный-цикл-вход-в-игру)).

---

## Как добавить новую сетевую команду

1. В `comm.lua`: функция отправки (`SendAddonMessage(self.prefix,
   "ИМЯ;параметр", "КАНАЛ")`) и функция `auction:Handle_ИМЯ(rest, sender)`.
   Регистрировать отдельно не нужно — диспетчер `HandleMessage` найдёт по
   имени.
2. Добавить строку в таблицу протокола выше (и в комментарий-шапку
   `comm.lua`) — иначе следующий человек не найдёт команду в документации.
3. Если команда меняет данные, которые показываются в UI — не забыть
   обновить UI (`RequestRefresh()`/`RefreshSignupButtons()` и т.п.) и, если
   нужно, сохранить (`RequestSaveData()`).

## Известные особенности и грабли

- **`GetConfiguredItemName`/`self.itemNames`** (`core.lua`) — мёртвый код,
  наследие старой системы кастомных названий предметов (до явки на босса).
  `self.itemNames` больше нигде не заполняется, функция всегда возвращает
  `nil`. Безопасно, но можно убрать вместе с одним вызовом в
  `GetCachedItemName`.
- **`auction.lastLM` не аутентифицирован** — см. раздел про роль ЛМ выше.
  Известное ограничение, не баг.
- **`journal.lua`/`queue.lua`** — если увидишь упоминания в старых
  версиях/бэкапах: это удалённые модули (журнал ставок, очередь токенов).
  **`lootmaster.lua`** тоже когда-то был удалён (старое окно раздачи с
  авто-списанием EP не работало), но сейчас файл есть снова — это полностью
  переписанная версия, см. раздел «Окно выдачи добычи». Старые бэкапы с тем же
  именем файла не подходят: они вызывали `GetMasterLootCandidate` в форме из
  поздних версий и путали порядок аргументов EPGP.
- **Имена боссов в `auction.instances` должны в точности совпадать с ключами
  `auction.bosses`.** Не дописывайте в имя пометки вроде «(не заполнено)»: выбор
  такого босса не находит свой список предметов, и `RefreshTable` сбрасывает
  выбор. Пометка для боссов без предметов рисуется отдельно, в дропдауне
  (`ui.lua`, по пустому списку в `auction.bosses`).
- **Высота окна по умолчанию — 605** (`auction.defaults.window.height` и две
  проверки `math.max(605, ...)` в `core.lua`): при меньшей высоте низ левой
  панели (с кнопками ЛМ и явки) может обрезаться.
- **Выпадающие списки `UIDropDownMenuTemplate` сами меняют высоту рамки.**
  `UIDropDownMenu_Initialize` вызывается при каждом открытии списка и ставит рамке 32 px.
  Если нужна другая высота (в тулбаре Attendance — 22), её надо возвращать: см.
  `LockDropdownHeight` в `attendance_ui.lua` (в функции построения пунктов и по
  `OnSizeChanged`). Ширина рамки при этом = `UIDropDownMenu_SetWidth` + 50.
- **Галочка `SkinCheckbox` не следит за `SetChecked`.** Она рисует свой значок и
  обновляет его только по клику и показу. После программной установки состояния
  вызывайте `box._epbaRefresh(box)` (см. `SetCheckboxChecked` в `attendance_ui.lua`).
  Свои обработчики клика вешайте через `HookScript`, а не `SetScript`.
- **Порядок файлов в `.toc` важен** — `core.lua` должен грузиться первым
  (создаёт `auction`), `events.lua` — последним (вешает обработчик событий,
  которому нужны уже существующие функции из всех остальных файлов).
- **`UpdateScrollFrameSize` и `GetCachedItemName` определены дважды** — в
  `core.lua` и в `ui.lua`. Так как `ui.lua` грузится позже, версии из
  `ui.lua` побеждают, версии из `core.lua` — мёртвый код (помечено прямо
  в коде). Для `UpdateScrollFrameSize` реализации идентичны (просто
  копипаста), для `GetCachedItemName` — **разные** (в `ui.lua` ещё
  кэшируется иконка). Если редактируешь одну из этих функций — редактируй
  версию в `ui.lua`, иначе правка не будет иметь эффекта.

## Отладка

- `auction.debug = true` в `core.lua` (или чекбокс в настройках) — включает
  подробный лог через `auction:Debug(...)` в чат (серым, `[EPBA DEBUG]`).
  Почти каждая сетевая и жизненно-цикловая функция логирует свои шаги —
  первое, что смотреть при "почему не работает".
- **Диагностика (`diag.lua`)**: `/epba diag` (или кнопка «Полная диагностика» в окне «Нашли баг?»).
  Вкладки: Сводка, Проверки (API клиента, роль ЛМ, целостность ставок/явки/посещаемости/резерва/журнала,
  EPGP-мост, таймеры), Лог (кольцевой буфер на 500 строк — `auction:Debug()` пишет в него всегда, в чат —
  только при `auction.debug`), Сеть (каждое исходящее/входящее сообщение, счётчики по командам, пик частоты,
  превышение лимита 255, неизвестные команды), Ошибки (xpcall вокруг таймеров и входящих сообщений +
  глобальный обработчик; со стеком), Рейд (опрос DPING/DPONG: версия, кого считает ЛМ, контрольная сумма
  ставок), Отчёт (всё важное одним текстом для вставки в баг-репорт). Ошибки и хвост журнала сохраняются в
  `EPBossAuctionSavedDiag` при выходе. Новая проверка = `Check("название", function() return "ok|warn|fail|info", "текст" end)`.
  `/epba diag chat | checks | log [текст] | net | errors | raid | report | clear | debug on/off`.
  diag.lua грузится после comm.lua/contacts.lua и переопределяет `Debug`, `ScheduleTimer`, `HandleMessage`,
  `GetDiagnosticsString`. `IsInRaid`/`IsInGroup` в core.lua подставляются, если клиент их не даёт (`auction.apiShims`).
- `/epgpfind` — сканирует `_G` в поисках EPGP-подобных таблиц, полезно при
  проблемах с получением EP на новом сервере/версии EPGP.

## Слэш-команды

| Команда | Действие |
|---|---|
| `/epba` | открыть/закрыть главное окно |
| `/epba bug` | окно с контактами для сообщений об ошибках (то же открывает кнопка «Нашли баг?» в шапке главного окна) |
| `/epba help` | окно «Справка» (то же открывает кнопка «?» в шапке главного окна, между «Настройки» и «Нашли баг?») |
| `/epbasave` | принудительно сохранить данные |
| `/epbaupdate` | принудительно обновить EP из EPGP |
| `/epbazoom+` / `/epbazoom-` / `/epbazoomreset` | масштаб окна |
| `/epbaoptions` | открыть панель настроек |
| `/epbaoffspec <0.1-1.0>` | коэффициент офф-спека (только ЛМ) |
| `/epbaloot` | показать окно добычи, если есть невыданные/несписанные записи (только ЛМ) |
| `/epbaloot test` | тестовое окно: выдача и списание имитируются, EPGP не трогается |
| `/epbaloot hide` | закрыть окно добычи (списанные записи очищаются) |
| `/epgpfind` | отладочный поиск EPGP-аддона в `_G` |
